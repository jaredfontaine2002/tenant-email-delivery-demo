Working prototype · work sample

CRM email that lands in the inbox, not the spam folder

A customer-management platform for small tour operators lives or dies on email: enquiries, quotes, itineraries and information packs all travel by email. When tenant messages are flagged as spam, the platform's core feature is broken. This demo prototypes the fix — the two ways a tenant can send, and the diagnostics that show whether either of them will actually deliver.

Check a domain now Set up a sending domain

Option one · integrated

Tenants send from their own domain

The tenant adds three DNS records — SPF, DKIM and DMARC — and the platform sends as bookings@theirtourcompany.com, fully authenticated. This is the scalable, deliverable lane: authentication aligns with the visible From domain, so DMARC passes and inbox placement follows.

Open the setup wizard → it generates the exact records and then verifies them against live DNS.

Option two · no integration

Tenants send from any address

“Just let me use my Gmail address” sounds simple and is the lane that lands in spam — unless it is done the one legitimate way: sending through the tenant's own connected mailbox (Google / Microsoft OAuth).

Read the design → why the naive version fails SPF/DKIM alignment, and the architecture that works instead. Labelled honestly: a design, not a working feature.

About this prototype

Built with Python and Flask, dnspython for live DNS lookups and the ZeptoMail transactional API — mirroring the server side of a typical tour-operator CRM stack (the production system this is modelled on pairs a React front end with a Python/Flask back end and Postgres). The tools here are deliberately stateless: no database, no accounts, nothing stored. It was built from the tenant's chair — by someone who runs a self-guided cycling tour company and answers to the same spam folder.
