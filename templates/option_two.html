Option two · no integration

“Send from any address” — the honest architecture

Some tenants will not touch DNS. They want to type their usual email address into the CRM and have messages “just send”. This page is a design, not a working feature — it explains the one way that lane can work legitimately, and why the obvious implementation is exactly what puts tenant mail in spam today.

The naive version — and why it fails

The tempting implementation is for the CRM's own servers to send mail with From: tenant@gmail.com (or the tenant's own domain) in the header. To the receiving server, that mail is indistinguishable from a forgery:

CRM server composes mail
From: tenant@theirtourcompany.com
→
Sent from the CRM's IPs
via the platform's mail service
→
Receiver checks alignment
SPF: sending IP is not in theirtourcompany.com's SPF ✗
DKIM: no valid signature for their domain ✗
→
DMARC fails
→ spam folder, or rejected outright

DMARC requires at least one of SPF or DKIM to pass and to align with the visible From domain. A platform cannot mint that alignment for a domain it does not control: it cannot add itself to the tenant's SPF record (that is the DNS step the tenant refused), and it cannot sign DKIM with a key the tenant never published. There is no header trick around this — that is the point of the system.

The legitimate version — send through the tenant's own mailbox

The one route that works: the CRM never pretends to be the tenant's domain. Instead the tenant connects their real mailbox once, and the CRM asks that mailbox to send.

Tenant clicks
“Connect Gmail / Outlook”
→
OAuth consent
Google / Microsoft sign-in,
send-only scope, revocable
→
CRM calls the mailbox API
Gmail API or Microsoft Graph
“send as me”
→
Mail genuinely leaves Google / Microsoft
SPF ✓ · DKIM ✓ · From aligned ✓
→
DMARC passes
→ inbox

Because the message truly originates from the tenant's own provider, the authentication is real rather than imitated: for a Google Workspace or Microsoft 365 tenant, SPF and DKIM align with their custom domain; for a plain gmail.com address, the mail is a genuine Gmail message. Either way the receiver's checks pass honestly.

What this design has to carry with it

  • Consent and revocation. OAuth tokens are stored encrypted, scoped to sending only, and the tenant can disconnect at any time — at which point the lane closes, visibly, in the product.
  • Volume ceilings. Mailbox APIs have daily sending quotas (hundreds to a couple of thousand messages a day, depending on the provider and account). Fine for enquiries and itineraries; not a bulk channel. High-volume tenants graduate to option one.
  • Sent-folder truth. Messages appear in the tenant's own Sent folder — a feature, not a bug: the tenant's records match what customers received.
  • Provider review. Google and Microsoft require app verification for mail scopes. That is a one-time platform cost, budgeted in the open rather than discovered mid-build.
  • The honest fallback. If a tenant will neither publish DNS records nor connect a mailbox, the remaining truthful option is a platform sending domain (e.g. via the platform's own domain with the tenant's name in the display name and replies routed back). It delivers — but it must be labelled as what it is, never dressed up as the tenant's own address.
